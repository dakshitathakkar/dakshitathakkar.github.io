ZSCALER / STAFF ROLE · IN PROGRESS01

A shared platform for incident lifecycle agents

I’m bringing the platform, persona-based agents, and evaluations together for incident lifecycle management.

In progressShared execution and agent evaluations under development.

LangGraphAgent infrastructureEvaluationsIncident lifecycle
Read case studyClose case study＋

The problem

Building agents for incident lifecycle management means thinking about more than each agent’s task. They need tools, context, and a runtime, and we need a way to assess how well they carry out their responsibilities. I’m working on those pieces together in my Staff role.

My approach

I’m developing a shared platform in LangGraph alongside the persona-based agents and their evaluations. The platform covers tool integration, context and memory, execution, observability, and guardrails. The aim is to give teams a common foundation while leaving room for the logic each agent needs.

The impact so far

The platform, agents, and evaluations are in progress. The work is focused on making execution easier to inspect and agent performance easier to assess across the incident lifecycle.

Reliability work

I’m also working on confidence quantification for agent trajectories. That sits alongside observability and evaluations as part of understanding how an agent reached a result and how much confidence to place in it.

ZSCALER / MCP & ON-CALL AGENTS02

Giving on-call agents the tools to act

I connected agents to the tools they needed and built multi-step workflows for our on-call teams.

Delivered8+ MCP servers · 3 multi-step agents

PythonMCPLangChainLangSmith
Read case studyClose case study＋

The problem

Our on-call agents needed access to operational tools and a way to use them across multiple steps. We also needed to follow their execution, so the result came with a view of what the agent had done.

My approach

I led the design and development of Python MCP servers, combining custom implementations with open-source integrations. I built the agents in Python and LangChain, working through model selection, temperature tuning, and tool orchestration. LangSmith and Weights & Biases gave me visibility into their execution.

The impact

I delivered 8+ MCP servers and three multi-step agents for on-call workflows. Together, they connected the AI Operations team’s agents to operational tools and supported work that needed several steps to complete.

ZSCALER / EVENT-DRIVEN SYSTEMS03

Processing 150,000 events a day

I built a Kafka-based engine to help our operational workflows handle more work each day.

Impact150K events/day · 80% higher throughput

KafkaEvent-driven architectureBackend systems
Read case studyClose case study＋

The problem

Our operational workflows needed to process a high volume of daily events. The practical question was how much work the engine could handle, so throughput was the measure that mattered for this project.

My approach

I implemented the workflow engine using Kafka and an event-driven architecture, building the backend that processes those operational events.

The impact

The engine handles 150,000 events per day, with an 80% improvement in throughput. That gave the workflows more processing capacity for their daily workload.

Related work: enterprise access control

Another part of my backend work was an authentication and authorization layer in Java and Spring Boot. I designed and implemented support for 8,000+ SSO users and 50+ services, including complex roles and permission hierarchies.

ZSCALER / BACKEND PERFORMANCE04

From a minute to under three seconds

I worked on the queries and pagination behind aggregation APIs that were keeping people waiting.

ImpactResponse time: ~1 minute → under 3 seconds

JavaSpringPostgreSQLHibernate/JPA
Read case studyClose case study＋

The problem

A minute is a long wait for an API response. Some of our aggregation-heavy endpoints were taking roughly that long, in platforms used for customer-facing data aggregation and self-service configuration.

My approach

I worked on the SQL queries and pagination strategies behind the slower endpoints. These were part of the microservice-based modules I developed with Java, Spring, Hibernate/JPA, and PostgreSQL, in a backend handling more than 500 concurrent processes.

The impact

The query and pagination improvements brought response times down from approximately one minute to under three seconds, making those aggregation endpoints much quicker to use.

Related work: self-service configuration

I also built REST and GraphQL APIs for user management and role-based access control. They let enterprise users manage their own configuration, reducing manual administrative effort by 90%.
